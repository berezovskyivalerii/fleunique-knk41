# Руководство по авторизации.
В проекте используются [JWT токены](https://www.jwt.io/introduction#what-is-json-web-token).

## Базовый концепт

### В чем различие access и refresh токенов?

Есть access token и refresh token. Оба токена выдаются пользователю после успешного sign in.
Access token используется для доступа пользователя к эндпоинтам, хранится мало времени, например 30 минут 
(access - доступ). Когда же refresh token используется для обноваления access token пользователя, хранится долго, если бы
не было refresh token, то пользователь должен был каждые 30 минут вводить заново пароль (refresh - обновить).

### Зачем нам проверять, доступен ли эндпоинт пользователю?

Во-первых, есть функции, которыми пользователь не может пользоваться, пока не войдет в аккаунт (например, просмотр истории своих заказов). Во-вторых, есть функции, которые не должны быть доступны обычным клиентам — например, создание новых товаров или просмотр списка всех пользователей. 

Для второго случая у нас предусмотрен флаг `is_admin` в базе данных. Когда пользователь обращается к защищенному эндпоинту, происходит следующее:
1. Система берет Access токен и достает из него только `ID` пользователя.
2. По этому `ID` делается запрос в базу данных.
3. Система проверяет значение поля `is_admin` у пользователя на данный момент. 

### Из чего состоят токены?

* **Access token**:
  Access token состоит из двух полей:
  1. `sub`: строка с `ID` пользователя.
  2. `exp`: timestamp который показывает когда истекает токен.


* **Refresh token**:
  Refresh token не имеет внутренних полей. Это обычная строка случайных символов из 32 бвйт. Вся информация о токене хранится в таблице БД.

### Как токены обновляются?

Когда access токен истекает, то backend возвращает 401, frontend перехватывает эту ошибку и отправляет запрос c refresh токеном в теле на получение нового access токена. Backend ищет токен в таблице БД, сравнивает текущее время с `expires_at` чтобы убедиться, что refresh token еще валидный, далее проверяет, что пользователь существует и он активный. После чего backend генерирует новый access token и возвращает пользователю.


### Как токены удаляются? 

Access token удаляется сам по себе когда истекает его срок действия. (30 минут)
Refresh token удаляется через endpoint /logout.


## Как это все раализовано в коде?

/register:
* api слой: FastAPI проверяет правильные ли пришли данные, если да, то передает их дальше в сервис.
* service слой: проверка не занят ли email. Генерирует hash для пароля и передает дальше в crud.
* crud слой: делает INSERT в таблицу и сохраняет изменения COMMIT и отдает готовую запись с id.

/login:
* api: Использует OAuth2PasswordRequestForm (стандарт для Swagger, поэтому email передается в поле username). Проверяет через слой сервиса правильность пароля и статус аккаунта. Если все ок — запрашивает генерацию токенов и отдает их клиенту в JSON.
* service: Создает access_token встраивая в него ID, генерирует refresh_token и вычисляет его время истекания, передает refresh_token дальше в crud.
* crud: записывает refresh_token в БД связывая его со строкой user_id.

/refresh:
* api: принимает refresh_token из тела запроса. получает от сервиса новый access_token и возвращает.
* service: проверяет, что если токен не существует или его срок годности (expires_at) уже истек — выбрасывает ошибку 401 (Unauthorized). Если все нормально, то генерирует access_token.
* crud: выполняет SELECT к таблице refresh_tokens, чтобы найти переданную строку.

/logout:
* api: принимает refresh_token который нужно удалить. возвращает статус 204 No Content.
* service: просто вызывает метод crud слоя.
* crud: удаляет строку с токеном, больше его обновить нельзя.
